# Mac Native Host 叶层验证证据

本叶层为 `ztools-mac-native/v1` / wire protocol 1 提供普通权限 Host 与每实例 Worker。Worker 索引键为 `(pluginId, ownerToken, generation, pluginInstanceId)`；同一插件实例的多个组件在该 Worker 内按 `(pluginId, dllId)` 分别缓存。`releaseOwner` 回收同一 owner、generation、instance 下跨插件的所有 Worker；插件维护租约通过 `releasePlugin` 回收该插件下全部 owner 的 Worker。取消帧也携带 pluginId，避免路由到另一插件的 Worker。

Main 的只读目录接口只在 Host 为 `ready` 时按大小写精确匹配已签名 Resources policy 中的 plugin/component ID，并返回相对路径和 SHA-256。组件路径、信任哈希和签名身份不来自 Renderer。policy 必须包含正式构建提供的 Team ID、App/Host/Worker Bundle ID、最低系统版本和组件目录；缺少配置时关闭能力，不填入猜测值。管理员 native 组件拒绝，不降级到普通 Worker。当前信任闭包只接受 Mach-O 声明的系统依赖，插件自带的动态依赖未纳入首期支持。

## 2026-10-07 同对象加载安全边界修正

此前的 `dlopen("/dev/fd/N")` 后再用 `proc_pidinfo` 比较映射 vnode 的实现不能证明加载前身份：dyld 可在 `dlopen` 返回前运行组件 initializer，事后检查发现不匹配时，initializer 副作用已经发生；Team ID 的 Library Validation 也不等价于 expected SHA-256 与实际执行对象的绑定。现有实现不再调用这条加载路径。

当前 `zt_mac_native_load_candidate_v1` 仅执行只读静态 trust preflight；preflight 成功后返回 `SAME_OBJECT_LOAD_UNPROVEN`，不调用 `dlopen`，也不设置 `same_object_load_proven` 或 `may_load`。尚无受支持且已验证的 Darwin API 能在 initializer 执行前证明 dyld 将映射的对象与已校验 FD 相同，所以即使 policy 有效、slice 获批，Main readiness 仍为 `same-object-load-unproven`，不创建 NativeHost。Native 组件目前没有生产可用路径；不能把 Windows synthetic ABI 或签名字符串测试当作该证明。

Universal packaging 明确记录 `nativeHostMode: disabled`。`--include-native-host`、`--native-*`、catalog 或身份配置请求会在构建前失败；verify 遇到完整或残缺的 Host/Worker/policy 组均拒绝；sign 遇到启用请求或实际组也会在输出预留和签名之前拒绝。没有 NativeGroup 的纯 JavaScript App staging/sign 流程仍可执行。当前不生成或密封 NativeHost policy。
