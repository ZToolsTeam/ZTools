# 代码规范

本文是客户端仓库的代码规范，适用于 `electron-client/`、`frontend/`、`packages/` 等所有目录。测试怎么写见 [测试](testing.md)，模块分工见 [架构概览](architecture.md)。开发插件时，界面规则另见插件仓库的 [界面规范](https://github.com/ZToolsTeam/ZTools-extensions/blob/main/docs/ui-guidelines.md)。

## 动手之前

- **保持简单**：先用能解决问题的最简单写法，不为想象中的需求提前抽象。动手前先找仓库里有没有现成的函数或服务，不重复造轮子。
- **先找根因**：修问题先复现、定位原因，再改原因所在的地方，不在表层打补丁绕过去。
- **界面改动先想清楚价值**：新增按钮、卡片、提示或交互步骤前，先回答「它帮用户更快完成什么」。答不上来就不加。
- **复杂改动先设计**：涉及状态、并发或多个模块时，先在 Issue 里写方案，至少列出：
  - 有哪些状态，怎么迁移；
  - 边界条件（空值、上限、超时、中途取消）；
  - 哪些操作不能同时执行，怎么防止；
  - 出错、超时、进程退出时怎么处理。

  拿不准的地方先讨论，确认后再写代码。

## 七项原则

1. **完整**：处理枚举和分支时考虑所有取值，保留 `default` / `else` 兜底。
2. **成对**：打开与关闭、注册与注销、订阅与取消订阅一一对应。正常结束、出错和退出三条路径都要清理。
3. **互斥**：不能并发执行的操作要有明确的锁或状态标记，防止重复触发。
4. **状态机**：状态变量要有初始值；改状态前先想清楚迁移关系。先检查、后使用的地方，注意中间状态是否已经变化。
5. **边界**：检查空值、零、最大值、溢出、并发、超时和中途取消。
6. **防御外部输入**：IPC 参数、文件内容、网络响应、命令行参数一律视为不可信，先校验再使用。出错时只影响当前操作，不拖垮其他功能。
7. **测试覆盖**：新功能和修复都要带测试，并覆盖异常情况，要求见 [测试](testing.md)。

另外三条：

- **不掩盖失败**：失败就返回错误，不用示例数据或假的成功结果顶替；不写空的 `catch {}` 吞掉错误，确实要忽略时写明原因。
- **不写本机信息**：代码、注释、日志和测试数据里不出现本机绝对路径、用户名、令牌或其他个人信息。
- **不复制大段代码**：需要复用一大段逻辑时，抽成共用的函数或模块，不要整段复制粘贴。

## 分层规则

### 主进程与预加载（`electron-client/`）

- **遵守安全基线**：窗口安全选项、预加载只暴露逐个方法、主进程按真实窗口判断调用方身份，见 [安全基线](architecture.md#安全基线)。`npm run test:quick` 的源码检查会拦下 `nodeIntegration: true`、`contextIsolation: false`，以及在预加载入口之外引用 `ipcRenderer` 的代码。
- **新增宿主方法一次改齐**：同时改 [`electron-client/src/contracts/`](../electron-client/src/contracts/) 里的请求格式与调用方能力表、预加载和路由，步骤见 [一次调用怎么走](architecture.md#一次调用怎么走)。
- **长任务可取消**：耗时操作要支持取消；窗口销毁时停止并释放资源；应用退出时清理要有时间上限，并且重复调用也不会出错。
- **成对清理**：监听器、定时器、全局快捷键、系统钩子和子进程，注册的地方要有对应的清理。
- **TypeScript**：`electron-client` 开启了 `strict`，新代码不要新增显式 `any`。

### 界面层（`frontend/`）

- 使用 Vue 3 Composition API 和 `<script setup>`，不用 Options API。
- 新组件用多个单词命名，如 `PluginCard.vue`、`SearchBar.vue`。
- 状态管理用 Pinia；从 Store 解构响应式字段时用 `storeToRefs`，否则会失去响应性。
- 样式按这个顺序选：Ant Design Vue 组件 > 组件配合 TailwindCSS > 原生 HTML 加 TailwindCSS。
- `<style>` 加 `scoped`（或 `module`），避免污染全局样式。颜色用主题变量（如 `var(--rc-text-muted)`），不写死色值，深色和浅色主题才能自动切换。
- 组件里创建的定时器和事件监听，在 `onUnmounted` 中清理。
- 界面层拿不到 Node 模块，系统能力一律通过 `window.ztools` 调用。

### 声明式 UI（`packages/declarative-ui/`）

插件只用 `List`、`Detail`、`Form`、`ActionPanel`、`Action` 等组件描述界面，不操作 DOM，也不写 CSS，样式和主题由客户端统一渲染。改组件或运行时的时候，不要给插件开出直接操作 DOM 或注入样式的口子。

### 原生组件（`electron-client/native/`）

- 原生代码作为独立进程运行，通过管道与主进程通信，不加载进主进程。这样原生代码崩溃不会拖垮主进程。
- 主进程一侧把进程退出、超时、输出损坏当作一定会发生的情况来处理：当前请求返回错误，相关功能标记为不可用，其余功能照常运行。
- 原生进程同样校验收到的每一个参数，只执行登记过的操作。

## 格式与换行符

- 修改已有文件时保持原来的换行符（LF 或 CRLF），不要让编辑器自动改写。
- 新建文件统一用 LF；`.bat` 文件用 CRLF。
- 沿用所在文件的写法，不运行全仓批量格式化。格式调整不要夹在功能改动里。

## 提交说明

格式为 `类型: 说明`，也可以带范围：`类型(范围): 说明`。常用类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复问题 |
| `refactor` | 重构，不改变行为 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建、依赖、脚本等杂项 |

也接受 `perf`、`style`、`build`、`ci`、`revert`。说明用中文或英文都可以，写清楚改了什么，例如：

```text
fix(launcher): 修复快速连续唤醒时窗口闪烁
feat: add keyboard shortcut for clearing clipboard history
```

Pull Request 以 squash 方式合并，最终的提交标题由维护者整理。
